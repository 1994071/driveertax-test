### Automatic invoice reminders — 24 October 2026

Per-invoice consent is off by default. The invoice detail screen saves a reminder recipient separately from the immutable issued invoice. A background worker checks every ten minutes; eligible unpaid, unarchived invoices get one attempt on the due date and one on day seven overdue, between 09:00 and 18:00 Europe/London. Missed dates are not replayed. Mark paid promptly; restoring/undoing payment does not resend a stage already attempted.

Reminders are plain-text emails containing the number, gross total, due date and saved payment instructions, without attachments. They use the existing verified sender and shared `report_email` minute/day quotas (currently 20 emails per user/day and 200 globally/day across manual reports, invoice email and reminders). Quota-denied work remains eligible for another check that day. The worker processes up to five reminders per check. Review caps before scaling.

Settings and history have owner RLS. A Vault-generated, scope-limited scheduler token authenticates the worker; only its SHA-256 hash is readable by service_role. Anonymous/customer calls cannot run it. Database claims recheck eligibility and use a unique invoice/stage ledger; Resend gets an idempotency key. Accepted means provider acceptance, not inbox delivery. Failed/uncertain attempts are not automatically resent, avoiding duplicate reminders after ambiguous network outcomes; history tells the owner to check delivery before a manual follow-up. Switching off cannot recall in-flight mail.

Verification: mocked worker/UI tests and rollback-only live SQL tests cover authentication, quotas, paid/archive/off eligibility, owner isolation, UK hours, DST, duplicate claims and result history. Existing invoice/PDF/VAT tests pass. No real customer reminder has been sent by these tests. Device acceptance and a scheduled real reminder to an owner's test address remain to verify.

### Owner invoice push notifications — 24 October 2026

Profile → Your invoice notifications provides explicit device opt-in, sound preference, Enable/Save, Send test notification, and Turn off on this device. It is independent of per-invoice customer email consent. The device gets at most one summary attempt per UK day when active unpaid invoices are due/overdue, checked every ten minutes between 09:00 and 18:00 Europe/London. Paid, cancelled, archived and future invoices are excluded. Nothing due means no notification. Enabling after 9 am allows a summary on the next check. Daily attempts are not automatically retried after uncertain delivery; accepted by a push service is not proof of display. The test button sends a separate explicitly requested test and is rate-limited.

The app includes a manifest, Home Screen icons and a push-only service worker. No pages, financial API responses or receipts are cached offline. iPhone/iPad requires Home Screen installation and notification permission. OS mute/Focus/browser settings control background sounds; foreground and background notifications use the device notification sound when allowed. A sound cannot be guaranteed. Notifications show counts, without customer names or money amounts; opening them focuses the app and opens the invoice list after authentication/data loading.

Owner devices and delivery claims are service-only tables with client-deny RLS. Each API action verifies the user's token and filters by verified owner, ignoring caller-supplied user IDs. Push endpoints are HTTPS and allowlisted to known Apple/Google/Mozilla/Windows push hosts, with redirects disabled and bounded timeouts. The private VAPID signing key is generated once and stored in the client-inaccessible service configuration; never copy it to a public build or chat. Bootstrap/rotation must be performed securely and devices must resubscribe if the application-server key changes. The scheduler reuses the scope-limited Vault cron credential. Owner push network calls use a dedicated bounded quota; customer email quotas are unchanged.

A local worker binding protects shared-device account switches: mismatched/in-flight payloads display only a generic silent notification; a mismatched account/binding is always silent. Explicit signout clears the binding and unsubscribes the browser. Expired push endpoints are disabled on 404/410. Device metadata is retained until account deletion or an operator retention cleanup; subscription endpoints/keys should be included in the privacy data map/export process. Account deletion cascades these rows. Review provider processing, retention and real-device acceptance before launch.

Verification: mocked tests exercise real VAPID encryption with intercepted network, quota failure, origin/endpoint restrictions, owner-only tests, expired subscriptions, no private key disclosure, service-worker cross-account privacy, sound and click behavior, and enable/test/off UI. Live SQL tests roll back all fixtures and verify signing-key restrictions, owner/device binding, UK hours/DST, summary claims and daily deduplication. A live scheduler probe with zero subscribed devices sends no push. Actual lock-screen notification/sound/installation acceptance needs the user's device and permission.

Owner push device acceptance update: the first real iPhone test returned Apple HTTP 400 `BadWebPushTopic`. Removed the optional transport Topic header (display grouping still uses the service-worker notification tag). One controlled test addressed only the user's single enabled Apple subscription then returned HTTP 201 success. This confirms provider acceptance, not phone display or sound. The temporary operator diagnostic route was removed from the final deployed function; provider failures now expose only sanitized HTTP/reason codes, never endpoints or keys. Regression tests cover omitted Topic headers and failed response handling.

Owner sound correction: removed the rule that explicitly silenced native notifications while a window was focused. Sound-enabled, matched-account notifications now set `silent:false` and allow re-alerting in both foreground and background. Removed the separate foreground Web Audio message to avoid reliance on autoplay permission. Sound-disabled and account-mismatched notifications stay silent. Real iPhone sound acceptance is still pending.

## Job photos — 25 October 2026

- Home → Job photos creates customer job folders with date, address, notes and an optional link to an existing invoice. Invoice detail also opens the linked folder or starts one prefilled from the invoice. These actions do not change invoices, income or tax figures.
- Separate camera/library inputs, before/after/progress labels and photo notes. Browser conversion strips source metadata, flattens transparency on white and resizes to at most 1,600 pixels / 1 MB JPEG. Source limit 20 MB; very large or browser-unsupported formats show a useful error. Originals are not retained: keep full-resolution originals independently if needed.
- Private `job-photos` bucket; owner-only job/photo RLS and storage policies. No accountant access to customer job evidence in this version. Signed image previews expire in five minutes; reopening refreshes previews. Reports contain selected photos and their saved notes plus the job/customer details; no public gallery links.
- Limits enforced server-side: 200 job folders, 100 photos per job, 1,000 photos per account, 1 MB per stored image. Each image needs a counted metadata reservation before upload. Stored files must be removed before their metadata; interrupted uploads are shown for recovery/removal. No overwrite uploads. Archive keeps evidence; individual photo deletion is permanent and cannot recall shared PDFs.
- PDF generation uses authenticated downloads and real jsPDF, up to 30 selected photos per report. Native file sharing where supported; download fallback. Dates are labelled as upload dates, not verified capture timestamps. No video, AI notes, offline uploads, original-photo retention or capture-location evidence yet.
- Verified with rollback-only live DB fixtures: cross-owner reads/writes/uploads blocked, cross-owner invoice links blocked, immutable ownership/path columns, reserved upload access, storage-first deletion and per-job photo quota.
- Functional DOM tests cover job creation, safe text rendering, uploads/resizing dimensions, real JPEG/PDF generation, interrupted-upload recovery, deletion, archive and late account responses. Provider/canvas mocks are explicit. Browser binary download failed in this environment, so real iPhone/Android capture, compression quality, PDF sharing and mobile layout need device acceptance before broad release.
- Personal JSON exports include job/photo metadata; individual stored JPEGs can be downloaded from each photo card. Operator-handled full account deletion/export requests must include `customer_jobs`, `job_photos`, and the user's `job-photos/<user-id>/` files via the Storage API, alongside existing receipt/avatar cleanup. Account deletion remains an operator-reviewed request; do not assume database cascading deletes remove stored photo bytes.
