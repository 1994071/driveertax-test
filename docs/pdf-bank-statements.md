# PDF bank statement imports

Supports single-account GBP current-account bank statements, including downloaded and scanned PDFs. Limits: 5 MB, 10 pages, 200 transactions. Existing CSV support remains 2 MB / 500 rows. PDFs requiring an opening password, unreadable, multi-account, foreign-currency and credit-card documents are rejected. Permissions-encrypted bank PDFs that open with the empty password are decrypted by pinned unpdf/PDF.js and their positioned text is sent for extraction; scanned encrypted pages without usable text require an unlocked export. An image renamed to PDF is rejected by its contents. Standalone photo/JPG statements are not supported by this picker.

The upload dialog discloses automatic OpenAI processing before file selection. Selecting a new PDF starts reading automatically; a previously imported file shows a warning and requires the read button to continue. Standard CSV columns automatically open review, with manual mapping for unknown headers. The existing OPENAI_API_KEY server secret is reused. The authenticated parse-bank-statement Edge Function bounds the upload, validates PDF structure/page count, enforces a per-user quota, and asks for structured rows using the Responses API's input_file support. It requests store:false and never logs statement contents, uploads to public storage or writes financial records. This does not mean the provider has zero retention; applicable provider data controls still apply.

The user checks/corrects dates, descriptions, signed amounts and optional balances. When both balances are supplied, opening + all signed transactions must equal closing to the penny before review. Missing balances require explicit manual checking. Neither arithmetic nor a model's completeness flag proves that OCR is accurate. The review list groups by day or Monday–Sunday week, filters paid in/out, suggests editable driver expense categories, and totals the selected rows. Only ticked business transactions are saved on their original dates; unticked rows are skipped. Every accepted transaction still requires row approval using the existing bank importer; salary, transfers and existing matches default to Skip. The owner-scoped SHA-256 file lookup warns even after a rename. The new commit_bank_statement wrapper serializes saves and uses the original account identity for the same exact file, so changing its nickname cannot bypass row deduplication. Partial selections can be completed on a later import. PDF and CSV still share owner/account/date/description/direction/occurrence fingerprints, so keep the same account nickname for overlapping different files. Legacy files without a stored hash can only get a filename warning and candidate-record checks. Balances are never inserted as income or expenses.

The source PDF is processed but not retained in Earnavik's evidence storage. Keep the original. Saved records use the original filename in import history and support the existing undo safeguards.

Validation: mocked-provider tests cover exact-penny balance checks, malformed/oversized/over-page PDFs, auth/quota failures, incomplete responses and preview-only output. Phone browser tests cover automatic reading, corrections, completeness/approval gates, selective dated saves, duplicate-file notices, CSV fallback, filters, week grouping, network retry and account-switch isolation. Synthetic real AES-256 empty-password and opening-password PDFs test decryption versus rejection. Rollback-only database fixtures verify cross-format duplicate suppression. A real bank PDF still needs end-to-end device testing; only screenshots were supplied during this change.

Deployment: apply supabase/schema/bank_pdf_limits.sql and supabase/schema/bank_statement_hash.sql and deploy supabase/functions/parse-bank-statement with verify_jwt=false (the handler validates getUser itself, supporting current JWT keys). Publish the frontend build, which now includes bank-pdf-workspace.js. Until frontend publication is verified, do not describe PDF uploads as live.
